# GEO 监测平台后台数据库设计（Egg.js + Mongoose）

> 逆向自线上实测：49 个接口、749 次请求报文、前端 bundle、账户真实数据。
> 交付物 = 本文档 + 45 个可直接运行的 Mongoose model（`app/model/*.js`）+ 3 个 schedule + 6 个 pipeline service 骨架。

---

# 一、总体设计决策

## 1.1 为什么按「层」而不是按「页面」建表

实测数据显示：**同一个原始数据被 10+ 个页面以不同聚合口径消费**。例：一条 AI 回答的引用链接，同时喂给 引用源追溯页、信源平台偏好页、引用源洞察页、周报 sources 模块、信源库成本推荐、自有内容归因。因此数据库按**数据生命周期**分层，页面接口只做最后一公里聚合：

| 层 | 职责 | 关键集合 | 类比 |
|---|---|---|---|
| 配置层 | 谁、监测什么 | users/brands/monitor_queries/subscriptions | 输入参数 |
| 原始层 | 不可变的采集事实 | collect_slots/raw_answers/snapshots | 数据湖的 Raw 区 |
| 事实层 | NLP 解析出的结构化事实 | brand_mentions/opinions/citation_edges | DWD |
| 指标层 | 按"问题×引擎×天"预聚合 | daily_metric_*/source_daily_stats/leaderboard_dailies | DWS |
| 装配层 | 周/月报快照与分享 | reports | ADS |
| 行动层 | 写作/发稿/归因回流 | writing_jobs/articles_generated/publish_orders | 业务系统 |
| 资金层 | 积分/套餐/订单 | credit_accounts/payment_orders | 事务系统 |

## 1.2 MongoDB 契合点（为什么线上选它）

- `reports.payload`：18 个模块的混合大 JSON（15KB+），字段随模板版本漂移 → 用 Mixed 类型免迁移；
- `monitor_queries.question_list`：双形态嵌套数组天然文档结构；
- `raw_answers.answer_text`：长文本 + 高频追加写；
- 解析事实（mentions/opinions/edges）量大、schema 演化快 → 无表结构变更成本。

## 1.3 两个必须的隐藏基础设施

线上接口行为反推出两件 model 之外的东西：

1. **自增序列计数器集合** `counters`：`monitor_queries.query_id` 是全局数字（实测 37935/40150），需 `CounterModel.findOneAndUpdate({_id:'query_id'},{$inc:{seq:1}})`；
2. **消息队列**（egg schedule 只做触发，槽位执行走队列）：`geo.collect.slot` / `geo.parse.answer` 两个队列，保证 40 槽/品牌/天 的弹性执行与失败重试。

# 二、填充顺序总拓扑（按依赖关系的八阶段 DAG）

```
S0 账号开户
   └─► users, credit_accounts        ─┐
                                       │
S1 品牌建档（Onboarding，分钟级异步）   │
   └─► onboarding_tasks(状态机驱动)     │
       ├─► brands                      │
       ├─► brand_profiles / brand_aliases / brand_products   ← AI分析产出
       ├─► monitor_queries (首批, task_id溯源)                │
       ├─► mined_topics(挖掘候选)                             │
       └─► plans(配置) → payment_orders → subscriptions ──────┤
                                                             ▼
                          ┌──────────────── 每日定时流水线（T+N 循环）────────────────┐
                          │ S2 00:30 展开槽位   collect_tasks → collect_slots        │
                          │ S3 00:30~04:00 采集 raw_answers + snapshots              │
                          │ S4 04:00 解析       entities/mentions/opinions/topics/   │
                          │                     sources/articles/edges/evidence      │
                          │ S5 04:30 聚合       daily_metric_*/source_daily_stats/   │
                          │                     leaderboard_dailies + cite回流        │
                          │ S6 05:00 报告(仅周日/月末) reports → reminders            │
                          └──────────────────────────────────────────────────────────┘
                                                             │
S7 行动层（用户白天实时操作）                                   ▼
   ├─► mined_topics→monitor_queries（配置回流）     指标层/报告页展示
   ├─► writing_jobs → articles_generated            ▲
   ├─► publish_orders（冻结积分）                     │ cite_count 每日回写
   ├─► diagnosis_tasks（单次诊断）
   └─► evidence_items / brand_wikis / media_favs / user_click_events（全时段）
```

**核心依赖链**：`monitor_queries` 是 S2 的唯一输入源 → `collect_slots` 是 S3 的唯一执行单 → `raw_answers` 是 S4 的唯一原料 → `brand_mentions/opinions/citation_edges` 是 S5 的唯一聚合源 → `reports` 是只读装配。

# 三、逐阶段详解：每张表"何时由谁用什么数据怎么填"

## S0 账号开户（触发：注册/登录 API）

| 表 | 填充操作 | 原始数据 | 对应线上证据 |
|---|---|---|---|
| `users` | `create` | 手机号+密码（bcrypt） | JWT payload `{sub: uuid, exp: 7d}` |
| `credit_accounts` | 同事务初始化 `{gold:0,silver:0,frozen:0}` | — | /credit/account 实测双币模型 |
| `menu_configs` | 运维一次性灌入 34 条 | — | /user/menus 6.7KB 实测 |

## S1 品牌建档（Onboarding 异步状态机，前端轮询体现）

触发：`POST /user/brands/analyze`（或创建品牌表单），状态机写在 `onboarding_tasks.stage`：

```
crawl(爬官网+公开信息) → keyword(行业词生成) → query(问题生成) → overview → done
```

| 步骤 | 写表 | 操作细节 |
|---|---|---|
| 0. 建档 | `brands`(status=building) | 名称/行业/业务描述落档，`platforms` 默认5引擎 |
| 1. crawl | `onboarding_tasks.crawler_started_at/completed_at` → `brand_profiles` | 爬虫+LLM 产出：industry/description/scripts/tone（实测 `seeded_from_db:false` 表示AI生成）；`raw html` 建议另存 OSS |
| 2. keyword | `onboarding_tasks.keywords` | LLM 生成行业词（如"礼堂椅""课桌椅"） |
| 3. query | `monitor_queries` 首批 + `mined_topics`(source=onboarding) | 每个问题**双形态**写入：`platform_query`（实际发问："采购礼堂椅厂家推荐"）/`user_friendly`（展示："礼堂椅厂家推荐"）；`task_id` 记溯源；LLM 生成别名 → `brand_aliases`（宏祥盛誉/宏祥家具） |
| 4. overview | `brands.status=active` | onboarding 完成 |
| 5. 套餐 | `payment_orders`(order_type=new) → 支付回调 → `subscriptions` + `credit_transactions`(consume) | 入门版 query_limit=8 → **约束 monitor_queries 创建数**；实测该品牌 8/8 用满 |

> 💡 `/user/info` 返回里的 `crawler_started_at/keyword_gen_started_at` 就是该状态机字段的投影——所以**设计上是读 onboarding_tasks 组装，而非 users 表平铺**。

## S2 采集展开（每日 00:30 schedule）

输入：所有 `brands.status=active` ∩ 订阅未过期。
操作（已在 `app/schedule/daily_collect.js` 实现）：

| 写表 | 数据构造 |
|---|---|
| `collect_tasks` | `{brand_id,date}` upsert；`expected_slots = 启用问题数 × 引擎数 × 端数`（实测 7题×5引擎=35）|
| `collect_slots` | 每个问题 × 每个引擎展开一行，唯一键 `(brand_id,date,query_id,platform,end)`，`question_sent = platform_query`，status=pending → 推队列 |

**⚠️ 槽位是一起指标的分母**：`query_status=true 且 query_is_execute=true` 才展开——这就是"监控问题管理"页开关立刻影响次日分母的原因。

## S3 槽位执行（worker 消费队列，00:30~04:00）

| 写表 | 时机与数据 |
|---|---|
| `collect_slots` | 状态机 pending→running→ok/fail/empty；`mock_account_id` 记录用了哪个中立号（审计）；`attempts` 重试计数 |
| `raw_answers` | 拿到 AI 回答**立即全量原文落库**（`parsed:false`），同时存 `cited_urls[]`。原文不可变——解析错了可重跑 |
| `snapshots` | 截图传 OSS 后写 `{photo_url, oss_key, exec_date}` |

线上证据：`photo_url` 直连阿里云 OSS，命名 `2026-08-30_豆包_采购礼堂椅厂家推荐_xxx.jpg`。

## S4 凌晨解析（04:00，三条 NLP 流水线）

读：`raw_answers where parsed:false`。**每条回答同时过三条管线**：

### 流水线 A · 榜单抽取（industry 题）→ `rank_extract.js`

```
answer_text → LLM抽取有序名录[{name, position}]
  → 名实体归一：查 brand_aliases（命中→is_target=true）
  → 未知名词 upsert brand_entities(scope=discovered)   ← "自动发现229个竞品"的来源
  → 写 brand_mentions（一条位次=一行）
```

实测证据：`full_ranking_matrix` 返回的 `competitor` 字段（每题榜一竟品）与 `competitor_count:229` 互证。

### 流水线 B · 口碑拆解（brand 题）→ `reputation_extract.js`

> **本仓库实现口径（与线上不同）**：首登分析**不再生成 brand 口碑题**——口碑题必然含品牌名，AI 回答必然提到该品牌，等于自问自答，指标失真。
> 监控问题一律**行业中立**（提示词见 `docs/LLM调用点设计与提示词.md` LLM-04，代码兜底见 `packages/geo-agent/src/neutral.js`）。
> 流水线 B 的输入随之收敛为「中立问题里 AI **自发提及**该品牌的回答」；`monitor_queries.query_type` 枚举保留 `brand` 仅为兼容存量数据。

```
answer_text → LLM抽观点单元[{quote, label, polarity}]
  → 话题归并 upsert opinion_topics(label 唯一键, $addToSet variants)
  → 写 opinions（一条观点=一行，带 slot/query/platform/date）
```

实测证据：`reputation_data` 里话题 "交期快" 的 `variants_count:1` + `platforms.yuanbao:["交期快（现货3-7天）"]` 正是 topic归并+逐平台留原文 的结构。

### 流水线 C · 引用归一 + 自有归因 → `citation_extract.js`

```
cited_urls[] → normalizeUrl(去utm/锚点) → upsert cited_articles(canonical_url 唯一)
             → normalizeSource(域名→站点) → upsert canonical_sources
             → 比对本品牌 publish_orders.published_url → is_own 标记
             → 写 citation_edges
  副产：高被引优质文章 → upsert evidence_items(tag=top-cite)
```

实测证据：`own_article_count`（抖音源下 60 篇自有稿）、`own_source_count`、`is_brand_published` 概念全部来自这一步的 URL 比对。

## S5 聚合（04:30，把事实压成指标）→ `aggregate.js` 全实现

| 写表 | 读源 | 口径（全部实测验证） |
|---|---|---|
| `daily_metric_queries` | slots+mentions 按 (query,platform,end,date) 分组 | `mention_rate=12/35×100=34.29%`；`score=ΣrankWeights[position]` |
| `daily_metric_brands` | opinions 按 (platform,date) 分组 | ratio+rep_score(0-100)+risk |
| `source_daily_stats` | citation_edges 按 (source,platform,date) 分组 | ref_count/篇数/问题覆盖/自有篇数 |
| `leaderboard_dailies` | mentions 按 (query,date) 聚合所有实体 | 权重分排序→当日榜（`rank_weight_table` 默认用实测逆向 [40,20,20,16,16,13.33,10,10,8,8]）|
| `publish_orders.cite_count`（回写） | citation_edges is_own 计数 | ← 行动层数据的**归因回流点** |
| `media_channels.ref_count/cost_per_citation` | source_daily_stats 30天窗 | `cost=售价÷被引数`（实测抖音源 0.07） |

## S6 报告装配（周日/月末次日 05:00）→ `report_build.js`

读 S5 全部指标 + 上期 `reports`（环比基准，等价于接口里的 `cmp_start_date/cmp_end_date`），组装成一个大 payload 文档入 `reports`：

```
18键：id/label/range/trend/engines/metrics/monitor/sources/summary/writing
      /channels/terminals/competitors/generatedAt/sourceChanges/allSourceNames
      /competitorNote/knownSourceNames
```

`sourceChanges.lost/newIn` = 本期 `allSourceNames` 与上期的**集合差运算**（实测 added:220/dropped:233）。
完成 → `reports.status=ready` + 写 `reminders`。套餐过期品牌照跑但 `collection_status:no_data`（实测"食家缘"历史只读场景）。

## S7 行动层（用户白天实时操作，无固定时序）

| 用户动作 | 写表链 | 读（回给页面） |
|---|---|---|
| 话题挖掘页"生成" | `mined_topics`（LLM产候选+volume/competition_hint）→ 采纳转 `monitor_queries` | 话题挖掘页 |
| 新建稿件 | `writing_jobs`(starting→running→awaiting_user→completed，WS逐节点) → `articles_generated` | AGENT 页/稿件库 /api/articles（含 counters 六态计数）|
| 发布稿件 | **事务**：冻结积分(`credit_transactions` freeze) → `publish_orders`(pending) → 媒体回执 `published_url`(ok,扣减) 或 `fail_reason`(fail,解冻退回) | 发稿记录页 |
| 单次诊断 | `diagnosis_tasks`(web+mobile 双端跑批) + `payment_orders`(order_category=diagnosis,积分扣) | 诊断中心/报告页 |
| 上传资料/记忆 | `brand_libraries`/`brand_wikis` | 品牌页/AGENT 记忆页 |
| 任意页面进入 | `user_click_events` | 运营分析 |

**闭环归因点**：`publish_orders.published_url` 在次日 S4-C 环节被命中 → `citation_edges.is_own` → S5 回写 `cite_count` → S6 进 `reports.payload.writing.engineCitations` —— "发的稿有没有被 AI 引用"全链可追。

# 五、核心计算口径速查（与线上逐一对齐）

```text
① 分母（denominator） = 当日 active 问题数 × platforms × ends
   → 宏观 35 = 7×5×1(web)；周报 terminals 245 = 7×5×7天 ✅

② mention_rate  = 命中(is_target)槽位数 / denominator × 100  （12/35=34.29%）
   top3_rate    = 位次≤3 同理；first_rate = 位次=1 同理
   逐日趋势 = 按 date 切片重算分子分母

③ 位次权重分（榜单用）：score = Σ slot 级 rankScore(position)
   rankScore 查表 [40,20,20,16,16,13.33,10,10,8,8]（位置1~10，实测逆向）
   → leaderboard 按 score desc 得 rank；visibility_trend=目标实体逐日(score, rank)

④ 口碑 rep_score = round(positive_ratio×100)（单日单引擎 0/50/100 形态验证）
   risk 评级阈值（前端常量）：≥80 健康 / ≥60 中风险 / <60 高风险
   综合行 all = 全引擎桶一起算（实测 all=74 介于各引擎间 → 加权或按观点总数归 pool，用 pool 重算即可严丝合缝）

⑤ 环比 Delta = 本期聚合 - 上期等长聚合；trend: >0 up / =0 flat / <0 down
   （平均排名类指标 reverse=true：下降是好事）

⑥ 成本归因 cost_per_citation = 渠道 sell_price ÷ 近30天 ref_count

⑦ 报告 sourceChanges：added = 本期源集合 - 上期（实测 added 220/dropped 233）；
   knownSourceNames = media_channels 中已知渠道与 allSourceNames 的交集
```

# 六、工程化清单

## 6.1 必须有唯一索引防重（跑批幂等键）

- `collect_slots`：(brand_id, date, query_id, platform, end) —— 重跑/补跑不会双写
- `daily_metric_queries/daily_metric_brands/source_daily_stats/leaderboard_dailies`：业务键唯一 + **全部 updateOne(upsert)** 支持重跑
- `cited_articles.canonical_url` / `canonical_sources.canonical_source` / `opinion_topics.(brand_id,label)` / `brand_entities.canonical_name` —— S4 upsert 原点
- `monitor_queries.query_id` 走 counters 自增

## 6.2 事务点（Mongo 4.2+ 副本集事务）

- **发稿下单**：freeze(credit_transactions) + publish_orders.insert + credit_accounts.frozen+=N 三写必须原子
- **支付回调**：payment_orders.status=paid + credit_transactions + credit_accounts/subscriptions 原子
- S5 回写 cite_count 允许最终一致（幂等）

## 6.3 量级与存储估算（单品牌日）

| 集合 | 日增量/品牌 | 备注 |
|---|---|---|
| collect_slots / raw_answers | 40 | 文本均值 ~2KB → 年 100MB/品牌/原文 |
| brand_mentions | ≈40×榜单长度(~10)≈400 | 建议单字段行 |
| citation_edges | ≈600（实测周 4509） | 最大表，需 (brand_id,date) 联合索引 + 按月归档 |
